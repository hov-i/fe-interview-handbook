## Lazy Loading이 오히려 성능을 나쁘게 만드는 경우가 있나요?

- **카테고리**: Browser

### 답변

있습니다. **첫 화면에 보이는 이미지, 특히 LCP 후보 요소에 lazy를 걸면 LCP가 명확히 나빠집니다.**

`loading="lazy"`가 걸린 이미지는 브라우저가 레이아웃을 계산해 뷰포트와의 거리를 판단한 뒤에야 요청을 시작합니다. 즉 HTML 파싱 단계의 프리로드 스캐너가 미리 잡아가는 이점을 포기하게 됩니다. 원래라면 CSS 파싱과 병렬로 다운로드가 시작됐을 이미지가, 레이아웃 이후로 밀리면서 수백 ms를 손해 보게 됩니다.

그래서 실무 기준은 이렇게 갈립니다.

- **첫 뷰포트 이미지**: `loading="eager"` + `fetchpriority="high"`를 씁니다. 히어로 이미지나 리스트 최상단 썸네일이 여기 해당합니다.
- **스크롤해야 보이는 이미지**: `loading="lazy"` 또는 IntersectionObserver를 씁니다.

IntersectionObserver를 직접 쓸 때도 같은 함정이 있습니다. `src`를 `data-src`로 빼두면 초기 HTML에는 이미지 URL이 없으므로 프리로드 스캐너가 아예 인식하지 못합니다. 초기 화면 이미지에는 이 패턴을 쓰면 안 됩니다.

측정할 때도 주의할 점이 있습니다. lazy loading은 **총 전송량은 확실히 줄이지만 LCP는 개선을 보장하지 않습니다.** 두 지표를 분리해서 봐야 합니다.

## 이미지 포맷 변환은 빌드 타임, 서버, CDN 중 어디서 하는 게 좋을까요?

- **카테고리**: Network

### 답변

이미지의 출처에 따라 답이 달라집니다.

**정적 에셋(로고, 아이콘, 배너)** — 빌드 타임 변환이 맞습니다. 번들러 플러그인으로 WebP/AVIF를 미리 생성해두면 런타임 비용이 0이고, 결과물이 결정적이라 캐시 전략도 단순해집니다.

**사용자 업로드 이미지** — 빌드 시점에 존재하지 않으므로 업로드 시 서버에서 변환하거나, CDN에서 요청 시 변환합니다.

- *업로드 시 변환*: 저장 시점에 원본과 변환본을 함께 보관합니다. 조회가 항상 빠르고 예측 가능하지만, 나중에 규격을 바꾸면 전체 재처리가 필요합니다.
- *CDN 실시간 변환*: URL 파라미터로 포맷·사이즈를 지정하면 CDN이 변환 후 캐싱합니다. 유연하지만 첫 요청은 느리고(cache miss) 비용이 요청량에 비례합니다.

여기서 중요한 것이 **캐시 오염 문제**입니다. 서버가 `Accept: image/webp` 헤더를 보고 응답을 분기한다면, 반드시 `Vary: Accept`를 함께 내려야 합니다. 그러지 않으면 WebP를 지원하는 브라우저가 받아간 응답이 CDN에 캐싱되고, 이후 지원하지 않는 브라우저에도 그대로 내려가 이미지가 깨집니다.

반대로 `<picture>` 태그로 클라이언트가 고르게 하면 URL 자체가 달라지므로 이 문제가 없습니다. 그래서 인프라 제어권이 약한 상황에서는 `<picture>` 방식이 더 안전합니다.

기존에 이미 업로드된 이미지를 어떻게 처리할지도 반드시 정해야 합니다. 일괄 마이그레이션 배치를 돌리거나, 조회 시점에 없으면 그때 변환하는 lazy migration 중에서 선택합니다.

## Context API로 상태를 관리할 때 리렌더링 범위 문제는 왜 생기나요?

- **카테고리**: React

### 답변

Context는 **값이 바뀌면 그 Context를 구독하는 모든 컴포넌트가 리렌더됩니다.** 값의 어느 일부만 썼는지는 상관이 없습니다. `{ step, formData, setStep, setFormData }`를 한 Context에 담으면, `step`만 쓰는 컴포넌트도 `formData`가 바뀔 때마다 리렌더됩니다.

폼 퍼널처럼 입력값이 키 입력마다 바뀌는 구조에서는 이게 바로 체감됩니다. `React.memo`로도 막히지 않습니다. memo는 props 변경을 막는 것이고, Context 구독은 props 경로를 거치지 않기 때문입니다.

대응 방법은 세 가지입니다.

1. **Context 분리**: 자주 바뀌는 값과 거의 안 바뀌는 값을 다른 Context로 나눕니다. 특히 `dispatch`나 setter 함수는 값이 바뀌지 않으므로 별도 Context로 빼면 이를 쓰는 컴포넌트는 리렌더에서 완전히 빠집니다.
2. **value 메모이제이션**: `useMemo` 없이 객체 리터럴을 그대로 넘기면 Provider가 리렌더될 때마다 새 참조가 생겨 무조건 전파됩니다. 이건 최소 조건에 가깝습니다.
3. **구독 단위를 쪼개는 라이브러리**: Jotai, Zustand 등은 값 단위 구독이라 필요한 컴포넌트만 갱신됩니다.

정리하면 Context는 **테마, 로케일, 인증 정보처럼 자주 안 바뀌는 값을 트리 전체에 내려보내는 의존성 주입 도구**에 가깝고, 고빈도로 변하는 상태 저장소로 쓰기에는 구조적으로 맞지 않습니다.

## Recoil이나 Jotai 같은 atom 기반 상태관리는 Context와 무엇이 다른가요?

- **카테고리**: React

### 답변

핵심 차이는 **구독 단위**입니다.

Context는 Provider 하나가 값 전체를 들고 있고, 컴포넌트는 그 Context를 통째로 구독합니다. atom 기반은 상태를 최소 단위(atom)로 쪼개고, 컴포넌트는 자기가 쓰는 atom만 구독합니다. `userNameAtom`을 쓰는 컴포넌트는 `cartAtom`이 바뀌어도 리렌더되지 않습니다.

두 번째 차이는 **파생 상태**입니다. atom 기반은 selector(Recoil) 또는 파생 atom(Jotai)으로 "다른 atom들로부터 계산되는 값"을 선언할 수 있고, 의존하는 atom이 바뀔 때만 재계산되며 결과가 캐싱됩니다. Context에서 같은 것을 하려면 `useMemo`로 컴포넌트마다 직접 관리해야 합니다.

세 번째는 **상태 정의 위치**입니다. Context는 Provider를 트리 어디에 두느냐가 곧 상태의 스코프입니다. atom은 모듈 스코프에 선언되므로 컴포넌트 트리와 독립적이고, 어디서든 import해서 쓸 수 있습니다. 이게 장점이자 단점인데, 트리 밖에 있어서 SSR이나 테스트에서 상태 격리를 위한 별도 장치(Jotai의 `Provider`, Recoil의 `RecoilRoot`)가 필요합니다.

실무 판단 시 알아둘 점이 있습니다. **Recoil은 개발이 사실상 중단된 상태**입니다. 새 프로젝트라면 Jotai나 Zustand를 보는 게 맞고, 기존 Recoil 코드는 Jotai가 모델이 유사해 마이그레이션 부담이 상대적으로 작습니다.

- Jotai의 파생 atom과 `useMemo`의 차이는 무엇인가요?

## 화면이 느리다는 제보를 받았을 때 원인을 어떻게 특정하시겠어요?

- **카테고리**: Browser

### 답변

"느리다"를 먼저 쪼갭니다. 초기 진입이 느린 것, 인터랙션 반응이 느린 것, 스크롤이 버벅이는 것은 원인과 해법이 전부 다릅니다.

**1단계 — 지표로 좁히기**
Lighthouse나 실사용자 지표로 LCP(초기 표시), INP(인터랙션 응답), CLS(레이아웃 이동) 중 어디가 나쁜지 확인합니다. 이것만으로 조사 범위가 크게 줄어듭니다.

**2단계 — Performance 패널로 프로파일링**
녹화 후 어느 구간이 긴지 봅니다.

- **Scripting이 길다** → 무거운 계산이나 과도한 리렌더를 의심합니다. React DevTools Profiler로 어떤 컴포넌트가 몇 번 렌더됐는지 확인합니다.
- **Rendering(Layout)이 길다** → 레이아웃 계산 대상 노드가 너무 많거나, 강제 동기 레이아웃(레이아웃 스래싱)이 발생 중입니다. 반복문 안에서 `offsetHeight` 같은 값을 읽고 곧바로 스타일을 쓰는 패턴이 대표적입니다.
- **Painting이 길다** → 큰 영역의 리페인트를 의심합니다. `box-shadow`, `filter`, 대형 이미지 리사이즈 등이 원인이 됩니다.

**3단계 — 가설 검증**
DOM 노드 수가 원인이라 판단했다면 실제로 세어봅니다. 1만 개 리스트라면 Elements 패널에서 노드 수를 확인하고, 데이터를 100개로 줄여 렌더해 시간이 선형으로 줄어드는지 봅니다. 줄어들면 노드 수가 원인이 맞고 가상 스크롤이 해법이 됩니다. 안 줄어들면 데이터 가공 로직 쪽을 봐야 합니다.

핵심은 **해법을 먼저 정하고 원인을 끼워 맞추지 않는 것**입니다. 가상 스크롤은 노드 수가 병목일 때만 효과가 있고, 원인이 API 응답 지연이었다면 아무것도 나아지지 않습니다.

## 가상 스크롤을 적용하면 접근성 측면에서 어떤 문제가 생기나요?

- **카테고리**: HTML

### 답변

보이지 않는 아이템이 DOM에 아예 없기 때문에 **DOM 존재를 전제하는 기능이 전부 깨집니다.**

- **브라우저 검색(Ctrl+F)**: 렌더되지 않은 항목은 찾을 수 없습니다.
- **스크린리더**: 목록을 순회할 때 실제로는 20개만 존재하는 것으로 인식합니다. 전체가 1만 개라는 사실을 알 방법이 없습니다.
- **키보드 탐색**: Tab으로 이동하다가 렌더 범위를 벗어나면 포커스가 사라집니다. 포커스를 잃은 요소가 DOM에서 제거되면 포커스가 body로 튀어 위치를 잃습니다.
- **Ctrl+A / 텍스트 선택 후 복사**: 화면에 있는 것만 복사됩니다.

완화 방법은 있습니다.

1. `role="feed"` 또는 `role="listbox"`와 함께 `aria-setsize`(전체 개수), `aria-posinset`(현재 위치)을 각 아이템에 부여해 "지금 보이는 건 일부"라는 사실을 보조기술에 알립니다.
2. 페이지 내 검색을 자체 검색 UI로 대체합니다. 어차피 1만 개 리스트에서 Ctrl+F는 실용적이지 않으므로, 서버 검색을 제공하는 게 더 나은 경험입니다.
3. 포커스가 렌더 범위를 벗어나지 않도록 overscan을 충분히 두고, 아이템 제거 전에 포커스를 안전한 위치로 옮깁니다.

결론적으로 **가상 스크롤은 성능과 접근성의 트레이드오프**이며, 항목이 수천 개 이상이라 실질적으로 다른 선택지가 없을 때 쓰고 위 보완책을 함께 넣는 게 맞습니다. 100~200개 수준이면 굳이 도입하지 않는 편이 낫습니다.

## WebSocket을 쓸 때 재연결과 중복 구독은 어떻게 다루나요?

- **카테고리**: Network

### 답변

세 가지가 실무에서 반복적으로 문제가 됩니다.

**1. 리스너 정리 누락으로 인한 메모리 누수와 중복 처리**
컴포넌트에서 `socket.on('message', handler)`를 등록하고 언마운트 시 `off`하지 않으면, 재마운트할 때마다 핸들러가 쌓입니다. 메시지 하나에 setState가 N번 실행되는 식으로 나타납니다.

```js
useEffect(() => {
  const handler = (msg) => setMessages((prev) => [...prev, msg]);
  socket.on("message", handler);
  return () => socket.off("message", handler);
}, []);
```

`off`에 **등록할 때와 같은 함수 참조**를 넘겨야 한다는 게 함정입니다. 익명 함수를 인라인으로 넘기면 해제되지 않습니다.

**2. 재연결 시 구독 복원과 유실 메시지**
네트워크가 끊겼다 붙으면 소켓은 재연결되지만 서버 쪽 룸/채널 구독은 초기화되는 경우가 많습니다. `connect` 이벤트에서 구독을 다시 거는 로직이 필요합니다. 또 끊긴 동안의 메시지는 소켓으로 오지 않으므로, 재연결 시점에 마지막 수신 시각 이후 데이터를 REST로 한 번 동기화하는 패턴을 함께 씁니다.

**3. 재연결 폭주**
서버가 잠깐 죽었을 때 모든 클라이언트가 즉시 재시도하면 복구되자마자 다시 죽습니다. **지수 백오프와 지터**로 재시도 간격을 벌려야 합니다.

추가로 모바일 웹뷰에서는 백그라운드 전환 시 연결이 끊기므로, `visibilitychange`에서 연결 상태를 확인하고 필요하면 재연결하는 처리가 필요합니다.

## 대량의 비동기 작업 중 일부만 실패하면 어떻게 처리해야 하나요?

- **카테고리**: JavaScript

### 답변

`Promise.all`은 하나라도 reject되면 즉시 전체가 실패합니다. 문제는 **나머지 작업이 취소되는 게 아니라 그냥 결과만 버려진다**는 점입니다. 12개 언어를 번역하다 3번째가 실패하면, 나머지 9개는 이미 API를 호출했고 일부는 DB에 저장까지 됐는데 호출부는 "전부 실패"로 받습니다. 데이터가 어중간하게 남게 됩니다.

대응은 세 축입니다.

**1. 결과를 개별로 수집**
`Promise.allSettled`를 쓰면 각 작업의 성공·실패가 모두 담긴 배열을 받습니다. 어디까지 성공했는지 알 수 있어야 다음 판단이 가능합니다.

```js
const results = await Promise.allSettled(tasks);
const failed = results
  .map((r, i) => ({ r, i }))
  .filter(({ r }) => r.status === "rejected");
```

**2. 재시도는 실패한 것만, 백오프를 두고**
전체 재실행은 성공한 작업까지 다시 호출해 비용과 부하가 두 배가 됩니다. 실패 목록만 모아 지수 백오프로 재시도합니다. 이때 작업이 **멱등**해야 합니다. 같은 요청을 두 번 보내도 결과가 같도록 upsert나 요청 키 기반 중복 제거를 걸어둡니다.

**3. 부분 성공을 어떻게 볼지 미리 정하기**
이게 가장 중요합니다. 12개 언어 중 10개만 성공한 상태를 "성공"으로 둘 것인지, "실패"로 되돌릴 것인지는 도메인 결정입니다.

- *전부 아니면 무*: 하나라도 실패 시 트랜잭션을 롤백합니다. 데이터 정합성이 중요할 때 씁니다.
- *부분 허용*: 성공분은 저장하고 실패분은 상태 컬럼에 표시해 나중에 재처리합니다. 번역처럼 없어도 서비스가 동작하는 경우에 적합합니다.

후자를 택했다면 실패가 조용히 묻히지 않도록 **재처리 대기 목록과 로그**가 반드시 있어야 합니다.

### 꼬리질문

- 멱등성을 보장하려면 API를 어떻게 설계해야 하나요?
- 지수 백오프에 지터를 섞는 이유는 무엇인가요?
- `Promise.all`이 실패했을 때 이미 진행 중인 요청을 실제로 중단하려면?

## E2E 테스트가 간헐적으로 실패(flaky)하는 원인은 무엇이고 어떻게 줄이나요?

- **카테고리**: 기타

### 답변

flaky 테스트는 **신뢰를 잃는 순간 테스트 전체가 무의미해집니다.** 실패해도 "또 그거겠지" 하고 재실행하게 되면 진짜 버그를 놓치게 됩니다.

주요 원인과 대응은 다음과 같습니다.

**1. 고정 대기(`waitForTimeout`) 사용**
`sleep(2000)`은 느린 환경에서 실패하고 빠른 환경에서 시간을 낭비합니다. 조건 기반 대기로 바꿔야 합니다. Playwright의 로케이터는 자동 대기(auto-waiting)가 내장되어 있어 요소가 보이고 상호작용 가능해질 때까지 기다립니다. `expect(locator).toBeVisible()` 같은 웹 우선 단언도 재시도를 포함합니다.

**2. 테스트 간 상태 공유**
앞 테스트가 만든 데이터에 뒤 테스트가 의존하면 순서·병렬 실행에 따라 결과가 달라집니다. 각 테스트가 자기 데이터를 직접 준비하고 정리해야 합니다. 로그인 같은 공통 준비는 스토리지 상태를 저장해 재사용하면 속도도 같이 잡을 수 있습니다.

**3. 외부 의존성**
실제 API를 때리면 네트워크와 서버 상태에 결과가 좌우됩니다. 검증 대상이 프론트엔드 로직이라면 네트워크를 목킹해 응답을 고정하는 게 맞습니다. 반대로 통합 자체를 검증하려는 테스트라면 목킹하면 안 됩니다. **테스트마다 무엇을 검증하는지 명확히 나누는 게 먼저입니다.**

**4. 애니메이션과 시간 의존**
전환 애니메이션 도중 클릭하면 좌표가 어긋납니다. 테스트 환경에서 애니메이션을 끄거나, 시계를 고정해 날짜 의존 로직을 결정적으로 만듭니다.

운영 측면에서는 CI에서 실패 시 트레이스·스크린샷·비디오를 남기게 하고, 재시도 횟수를 1회 정도로 제한하되 **재시도로 통과한 테스트는 별도로 집계**해 방치되지 않게 합니다.

### 꼬리질문

- E2E, 통합, 단위 테스트의 비중을 어떻게 가져가시나요?
- 어떤 기능을 E2E 대상으로 고르는 기준이 있나요?
- 테스트가 느려서 CI가 오래 걸린다면 무엇부터 손보시겠어요?

## 웹 접근성을 실제로 검증하려면 무엇을 어떻게 확인해야 하나요?

- **카테고리**: HTML

### 답변

자동 검사 도구는 **전체 접근성 이슈의 일부만 잡습니다.** Lighthouse나 axe는 대체 텍스트 누락, 명도 대비, 라벨 없는 입력처럼 기계적으로 판정 가능한 항목만 확인합니다. 대체 텍스트가 "이미지1"처럼 무의미해도 통과하고, 포커스 순서가 시각적 순서와 어긋나도 잡지 못합니다.

실무에서 밟는 순서는 다음과 같습니다.

**1. 자동 검사로 바닥 깔기**
axe DevTools나 Lighthouse로 명백한 위반을 먼저 제거합니다. CI에 붙이면 회귀를 막을 수 있습니다.

**2. 키보드만으로 전체 플로우 통과**
마우스를 놓고 Tab, Shift+Tab, Enter, Space, Esc, 방향키만으로 주요 시나리오를 끝까지 수행합니다. 여기서 대부분의 실제 문제가 드러납니다.

- 포커스 링이 보이는가 (`outline: none`만 걸고 대체 스타일을 안 준 경우가 흔합니다)
- 포커스 순서가 시각적 순서와 일치하는가
- 모달을 열면 포커스가 안으로 들어가고, 닫으면 열었던 버튼으로 돌아오는가
- 모달 밖으로 Tab이 빠져나가지 않는가(포커스 트랩)
- `div`에 onClick만 붙여 키보드로 못 누르는 요소가 없는가

**3. 스크린리더로 실제 청취**
macOS VoiceOver, Windows NVDA로 화면을 안 보고 들어봅니다. 버튼이 "버튼"으로만 읽히거나, 동적으로 바뀐 영역이 안 읽히는(`aria-live` 누락) 문제가 여기서 나옵니다.

**4. 시맨틱 우선 원칙**
ARIA는 보완재입니다. `role="button"` + `tabindex` + 키 이벤트를 직접 구현하는 것보다 `<button>`을 쓰는 게 항상 낫습니다. **잘못 쓴 ARIA는 없는 것보다 나쁘다**는 게 W3C의 첫 번째 규칙입니다.

국내 공공·금융 서비스는 KWCAG 2.2를 기준으로 심사를 받으므로, 해당 지침 항목별 체크리스트를 두고 확인하는 방식이 실무에 가깝습니다.

- 포커스 트랩은 어떻게 구현하나요?
